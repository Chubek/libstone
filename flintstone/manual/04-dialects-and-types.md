# 4. Types, dialects and target parameters

The C++ API is declared in `Flintstone.hpp`. A `Registry` owns dialect
definitions, operation contracts, lowering rules and backend callbacks. It is
initialized with the builtin dialects and VM backends. No process-global mutable
registry is used. Modules contain parameter overrides, not pointers into the
registry, and remain ordinary owning values.

## Register a dialect

The following complete declaration introduces a parameterized integer operation:

```cpp
flintstone::Registry registry;
flintstone::DialectDefinition toy;
toy.name = "toy";
toy.parameters = {{"amount", std::int64_t(7)}};

flintstone::OperationDefinition offset;
offset.name = "toy.offset";
offset.level = flintstone::Level::High;
offset.min_operands = offset.max_operands = 1;
offset.min_results = offset.max_results = 1;
offset.effect = flintstone::Effect::Pure;
offset.verify = [](const auto& operation, const auto& context) {
    auto type = context.type(operation.operands.at(0));
    if (type != flintstone::Type::integer(32) ||
        operation.results.at(0).type != type ||
        !operation.attributes.empty())
        throw flintstone::Error("toy.type", "offset requires i32");
};
toy.operations.push_back(offset);
registry.add_dialect(std::move(toy));
```

A module can now declare:

```text
dialect toy { amount = 12; }
```

The resolved `OperationContext::dialect_parameters` includes defaults and
overrides. `context.module.target` exposes the selected target's layout,
features and application parameters. An operation can check target legality
without baking machine facts into the generic IL.

Dialect identities are unqualified names and have a positive version field.
Every operation must belong to that dialect's namespace. Duplicate dialects,
operation names, invalid arity ranges and invalid levels are rejected before
normal registry insertion. Versions are host metadata; no automatic migration
of serialized dialect semantics is implied.

## Parameter contracts

`DialectDefinition::parameters` declares the allowed keys and their default
attribute variants. Unknown keys and wrong variants fail verification. An
optional `verify_parameters` callback performs semantic/range checks against
the target. For example, `arith.overflow` defaults to `"modular"`; no other
integer overflow policy is currently accepted.

Parameters of type `Type` participate in module substitution. This permits an
operation or opaque type to depend on a module type binding without reparsing
or re-registering the dialect. A callback sees resolved types, not unresolved
`param<T>` leaves.

The supplied high-level `math` dialect demonstrates operationally meaningful
parameterization: changing `factor` changes the constant generated by
`math.scale`. The factor must fit the signed representation of its i2–i64
result type. `math` also supplies `square`, `madd`, `cube` and `abs`, all
lowered to verified `arith` sequences (`abs` needs a comparison, a negation
and a selection with two temporaries).

## Shipped dialects

The default registry contains one dialect per type domain:

| Dialect | Level | Operations | Execution |
| --- | --- | --- | --- |
| `arith` | Core | scalar integer/float arithmetic, comparisons, select, constants, copies | VM directly |
| `cf` | Core + `trap` at High | phi, jump, branch, trap | VM (trap lowers to a throwing call) |
| `func` | Core | call, return | VM directly |
| `mem` | Core | load, store over `ptr<generic>` | VM heap cells |
| `math` | High | square, madd, scale, cube, abs over `i2`–`i64` | lowered to `arith` |
| `vector` | High | splat, add/sub/mul/div/mod/neg, extract over `vector<1..256, i2..i64\|f64>` | `vector_scalarize_pass`, then VM |
| `tuple` | High | build (1–64 scalar fields), extract | `tuple_sroa_pass`, then VM |
| `ptr` | Core | pointer + integer offset arithmetic | native targets only |
| `atomic` | Core | loads/stores with explicit ordering | native targets only |
| `vm` | Machine | mirror of the scalar core operations | VM bytecode |

`vector` lane counts are bounded to 256 so unrolling cannot explode operation
counts silently; the scalarizer additionally enforces a work budget. Tuple
fields must be integer, float or pointer scalars — nested aggregates are
rejected. Both eliminations handle loop-carried values through per-lane/field
phis, but values that escape the function (parameters, results, call
arguments, stored values) fail with `vector.escape`/`tuple.escape` rather
than changing signatures. Run the passes explicitly (or `--scalarize`); neither
`lower()` nor `execute()` invents them silently. `List` them at runtime with
`Registry::dialect_names()` or `--list-dialects`.

## Opaque and aggregate types

`DialectDefinition::verify_type` accepts or rejects a fully parameterized opaque
type. For example:

```cpp
toy.verify_type = [](const flintstone::Type& type,
                     const flintstone::Attributes&, const flintstone::Target&) {
    return type.name == "toy.box" && type.elements.size() == 1 &&
           type.elements[0] == flintstone::Type::integer(32);
};
```

Install this callback before registering the dialect. Without a callback,
opaque types in its namespace are not automatically valid. Tuple/vector
structure is checked independently; aggregate layout does not create arithmetic
or execution semantics for it.

`Type::parameter("T")` resolves through `Module::type_bindings`. Resolution:

1. rejects unknown parameters;
2. follows aliases and recursively substitutes element types;
3. rejects recursive/occurs cycles, including indirect cycles;
4. enforces the 64-level type nesting and total expansion-node bounds;
5. resolves `index` using `Target::index_bits`.

All bindings are checked, even if a particular function does not use them.
Bindings may describe a concrete signature, not an implicit runtime generic
calling convention. To compile two instantiations, copy the module, change its
bindings, specialize each copy and assign distinct exported function names as
appropriate.

## Target parameters and data layout

`Target` has an explicit name, pointer width, index width, endianness, feature
set and typed parameter map. Valid pointer widths are powers of two from 8 to
128; index widths are 2–64. The module verifier does not assume that a named ISA
supports every operation. Its backend must check actual target capabilities.

`layout(type, target)` implements Flintstone's **portable storage convention**:

- integer/float scalar size is `ceil(bits/8)`;
- pointers/indices use the explicit target widths;
- scalar alignment is the next power of two capped at eight bytes;
- vector size is element size times element count, with element alignment;
- tuples insert alignment padding and round total size to aggregate alignment;
- arithmetic overflow in size/padding computations is rejected.

This convention is not the platform C ABI, a SIMD ABI, or processor timing data.
Native backends must use authoritative ABI/type-layout information where it
differs. Opaque/unspecialized parameter layouts fail explicitly; applications
provide their own layout adapter for those types. Arbitrary target parameters
are supplied to callbacks but are not silently interpreted as new layout rules.

## Operation contracts

An `OperationDefinition` supplies:

| Field | Purpose |
| --- | --- |
| `level` | Stage at which the operation lives. |
| Operand/result intervals | Structural arity, including variadic and multi-result operations. |
| `effect` | Purity/effect contract used by transformations such as DCE. |
| `terminator` | Explicit CFG termination behavior. |
| `phi` | Predecessor-labelled edge-use semantics. |
| `verify` | Domain-specific type, attribute and target checking. |
| `ssa_opcode` | Optional assertion of exact scalar Firestone semantics. |

The verifier checks arity before invoking the operation callback, and checks SSA
definitions and operand types before allowing callback type lookup. A callback
should still use bounds-checked access when inspecting its own attributes.
Throw `flintstone::Error` to preserve a specific diagnostic code.

`ssa_opcode` is not a mnemonic-name matcher. Set it only when the operation is
semantically equivalent to that scalar Firestone operation. Domain operations,
overloaded arithmetic and multi-result operations should instead supply an
explicit lowering rule. Marking an effectful operation `Pure` authorizes its
deletion when unused: this is a semantic promise by the dialect author.
